📖 Bem-vindo ao Enigmic: Bug Hunt!

Este é um jogo colaborativo de investigação de bugs. Seu time precisa usar a lógica dedutiva para descobrir qual é a verdadeira causa raiz analisando as evidências.

Cada jogador tem um papel importante na decodificação do puzzle. Vocês trabalham juntos para marcar as pistas e eliminar as impossibilidades.

Cenário: Sistema de venda de passagens reporta anomalia crítica.

Sintoma: Usuários conseguem comprar o MESMO assento duas vezes.

Impacto: 47 conflitos detectados em 23 minutos.

Sua missão: Deduzir qual é a causa raiz analisando os sintomas.

🎮 Como o Puzzle Funciona

O puzzle é uma matriz de sintomas vs causas. Você vai preencher as células marcando se acha que cada causa pode ter gerado cada sintoma.

Linhas = Sintomas observados (evidências)

  • ✓ Ambos usuários recebem HTTP 200 OK
  • ✓ Janela de 100ms entre transações
  • ✓ Dois assentos iguais foram vendidos
  • ✓ Logs mostram dois commits simultâneos

Colunas = Possíveis Causas (suspeitos)

  • ▶ Lock de DB Não Liberado
  • ▶ Cache Desatualizado
  • ▶ Falta de Idempotência
  • ▶ Sincronização RPC Lenta

Cruzando os dados: Você marca cada célula indicando se AQUELE sintoma aponta para AQUELA causa.

✓ ✗ ? Os Três Estados

Cada célula do puzzle pode estar em um de três estados:

✓ SIM — Esta causa provavelmente gera este sintoma

✗ NÃO — Esta causa NÃO pode gerar este sintoma (eliminada)

? TALVEZ — Ainda não tem certeza, precisa mais informação

Interpretação: Sintoma 1 aponta para Causa A (✓), descarta Causa B (✗) e Causa C ainda é incerta (?)

🧠 Regras de Dedução Lógica

O puzzle segue regras simples de lógica que te ajudam a resolver:

  • Regra 1 - Uma causa por sintoma: Se você descobrir que um sintoma vem de uma causa específica (✓), todos os outros suspeitos naquela linha devem ser descartados (✗).
  • Regra 2 - Uma solução única: Apenas UMA causa é a verdadeira culpada. Se descartou 3, a última deve ser SIM.
  • Regra 3 - Consistência: Se uma causa é SIM em um sintoma, verifique se faz sentido nos outros sintomas também.

    • Dica de estratégia: Comece eliminando as possibilidades óbvias com ✗, depois veja o que sobra!

    💡 Exemplo Prático de Dedução

    Dica 1: "HTTP 200 OK em ambos os usuários"

    → Se a resposta foi 200 OK, não é problema de timeout (Sincronização RPC Lenta seria erro 504). Logo: ✗ NÃO é Sincronização RPC Lenta

    Dica 2: "Janela de 100ms entre transações"

    → Uma janela de 100ms é super pequena. Cache com TTL errado demoraria mais. Logo: ✗ NÃO é Cache Desatualizado

    Dica 3: "Dois commits simultâneos no banco de dados"

    → Se dois commits chegaram ao banco, não é problema de idempotência (seria rejeitado). Logo: ✗ NÃO é Falta de Idempotência

    Conclusão:

    ✓ Sobrou apenas uma: Lock de DB Não Liberado — ESSA É A RESPOSTA!
